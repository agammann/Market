# Disposable XMR verification harness

Prepared for one bounded GitHub Ubuntu24.04 run. This is exploratory verification code, not Market's supported deployment procedure. No actual XMR success is implied by syntax checks or preparation.

Proposed branch: `verification/xmr-fakechain-20261002`. Copy `prepare.py`, `run.sh`, `sanitize.py`, `verify.mjs`, `registry-metadata.json`, `package.json`, `package-lock.json` and this file into `.qa/xmr/`. The separately reviewed `xmr-hosted-check.yml` belongs at `.github/workflows/xmr-hosted-check.yml`. Publishing the workflow on that exact branch triggers one run; do not push it until the runner attempt is authorized and the frozen files are reviewed. No product source files change, and this branch need not be merged.

The app checkout is fixed at `8d22844f8c5f41caea40b5f857220db742109ef3`. Node is 24.19.0. Playwright1.63.0 and pnpm11.19.0 have npm integrity lock entries. Official publisher image manifests for BTCPay2.4.4, Monero0.18.4.3, Tor0.4.9.13, PostgreSQL18.4, Bitcoin31.1-1 and NBXplorer2.6.10 are pinned by Linux/amd64 digest. Registry metadata was read without downloading layers. The Monero plugin archive is official build17 from source `7824ff4481c75d171499b7bf69c532f9362dcd1e`, SHA256 `d83074f45a05e595ef41b981ebab367f4e70d3406ed7fb724102a315bdb4a736`; the runner downloads and verifies it before extraction. Chromium uses the GitHub image's preinstalled Google Chrome and records its actual version.

The runner is disposable. Linux containers share its host network; every configured service binds loopback. This is deliberately distinct from production Compose isolation. The app runs in the exact source checkout. Tor has separate generated app/provider onion identities. Monero uses `--regtest --offline --fixed-difficulty=1`, with runtime `nettype=fakechain` and zero peer checks before each block/transfer operation. Only generated wallets and account credentials are used. Each transfer is bounded to at most1XMR on the fakechain; no transfer operation is retried automatically.

The harness creates a provider account/store, enables XMR with10 confirmations, and imports a freshly generated invoice-only key through Market's administrator CLI. It registers three fictional accounts in the browser through Tor, uploads a digital file, creates a physical listing, moderates each, and creates actual XMR invoices. It checks unpaid/other-account denial; pays each exact provider amount using a real wallet; generates12 confirmation blocks; verifies BTCPay settlement and app state; downloads exact bytes as the buyer; and drives physical shipment/receipt/review through the browser. Generated blocks and transfers do not contact a public coin network.

Hard limits:60minute job,55minute wrapper,15minute image pull,8minute app install,4minute build,25minute browser/chain harness. Readiness polling is bounded; it never retries order creation, account creation or payment. A deadline or setup failure stays a failed attempt.

Only `report.json` and `pins.json` are uploaded. Runtime logs, wallet files, account passwords, keys, onion identities, database, browser sessions and invoices are excluded. Cleanup targets only the generated Compose project and runtime directory. The report retains the failed stage and sanitized error category; raw failures remain private to the disposable runner. No owner secrets or repository write token is passed into the harness.

Remaining limits even after a successful run: mainnet, actual physical delivery, security audit, arbitrary provider configurations and Linux backup/restore are not covered. Both service readiness and current rendered selectors remain unverified until the real run.
